### 3.2 Tool calling (tiếng Việt)

Probe `dev/vm/llm/tool-call-probe.json` có hai tool (`get_weather`, `fs_search`),
system prompt trung tính ("Dùng tool khi cần"), câu hỏi không gợi tên tool:
"Tìm giúp tôi các file PDF có chữ "hợp đồng" trong thư mục Tài liệu." Mô hình phải
tự chọn đúng tool và điền args.

```bash
curl -s 127.0.0.1:8081/v1/chat/completions -d @dev/vm/llm/tool-call-probe.json | jq .choices[0].message.tool_calls
```

```json
[
  {
    "type": "function",
    "function": {
      "name": "fs_search",
      "arguments": "{\"query\":\"hợp đồng\",\"path\":\"Tài liệu\",\"extension\":\"pdf\"}"
    },
    "id": "IeHEBEiWF1Cy3tYdLiIMzubw3dqZ7hIc"
  }
]
```

`finish_reason = tool_calls`, `usage = 316 prompt token / 37 completion token`.
Đúng tên tool, args là JSON hợp lệ, giữ nguyên dấu tiếng Việt. Probe cũ (một tool
`get_weather`, câu hỏi "Thời tiết hôm nay ở Hà Nội thế nào?") cũng trả
`get_weather` với `{"location":"Hà Nội"}`.

## 5. Nhận xét và rủi ro cần biết

1. **Tường lửa IP của systemd không có tác dụng với unit user.**
   `systemctl --user show aios-llm-chat -p IPAddressDeny -p IPAddressAllow` trả về
   `IPAddressDeny=0.0.0.0/0 ::/0` và `IPAddressAllow=127.0.0.0/8 ::1/128` (đúng ý
   thiết kế), nhưng systemd chỉ cài bộ lọc BPF cho unit của **system manager**;
   user manager chỉ ghi cảnh báo `unit configures an IP firewall, but not running
   as root`. Kiểm chéo bằng `sudo bpftool cgroup show <cgroup của unit>`: **không có program
   nào** gắn vào. Thử ra mạng thật:
   `systemd-run --user --wait --pipe -p IPAddressDeny=any -p IPAddressAllow=localhost curl https://huggingface.co`
   trả **HTTP 200** → IP **không** bị lọc. Muốn lọc IP thật thì phải nâng
   unit lên system manager (`sudo`); \[Unverified\] chưa thử được trong VM vì
   `sudo systemd-run` trả `Connection reset by peer`. Các mục sandbox khác **có**
   hiệu lực ở unit user (kiểm trong mount namespace của tiến trình): `/` và
   thư mục mô hình `ro` (`touch` → `Read-only file system`), `/home` không đọc được,
   `/tmp` riêng, `NoNewPrivs: 1`, `MemoryMax` = 4 GiB / 1,5 GiB.
2. **`MemoryCurrent` không phản ánh đúng RSS.** `memory.stat` của cgroup unit cho
   `anon = 1 302 351 872 B` (1,21 GiB), `file` = 0–14 MiB, `file_mapped = 0`: các
   trang page cache của file mô hình mmap bị tính ở cgroup gốc
   (`/sys/fs/cgroup/memory.stat` → `file` = 5,42 GB). Vì vậy `MemoryMax=4G` chỉ
   ràng buộc phần bị tính vào cgroup unit, không phải toàn bộ RSS 3,5–3,8 GiB.
   Trên máy boot mới, nếu trang cache của file mô hình bị tính vào cgroup của unit
   thì `MemoryCurrent` có thể lên ~3,7 GiB — gần trần 4 GiB. Nên cân nhắc nâng
   trần hoặc giảm `-c` khi lên M1.
3. **Bộ nhớ tăng theo độ dài ngữ cảnh.** Một prompt ~8k token làm `anon` tăng từ
   1,21 GiB lên 1,48 GiB (KV cache), RSS lên 3,81 GiB. Vẫn dưới trần:
   `memory.events` cho `oom_kill = 0`, `NRestarts = 0`.
4. **Độ trễ không đại diện cho phần cứng mục tiêu.** VM là arm64 ảo, 4 vCPU, chỉ
   backend CPU, không Vulkan. Trên laptop x86_64 + iGPU (Vulkan) sẽ nhanh hơn nhiều;
   ngưỡng chính thức của S-13 chờ đo ở M1/M2.
5. **Prompt cache của llama-server làm lần gọi sau nhanh hơn lần đầu**
   (6,25 s → 4,43 s trong lần đo cuối) vì cùng một tiền tố prompt. Số trung bình
   5,45 s vì vậy lạc quan hơn một cuộc gọi "lạnh".
6. **S-13 đầy đủ cần llama.cpp mới hơn b6153** (để có arch `qwen3_5`) và GPU
   Vulkan; gói `llama-cpp` của Fedora 44 hiện tại chưa đạt.
7. **Embedding e5:** probe đo dùng chuỗi trần. Thêm tiền tố `query:` làm độ
   tương đồng cặp liên quan tăng nhẹ (0,901 → 0,928); Hindsight nên theo đúng hướng
   dẫn của e5 (`query:` / `passage:`) khi dùng.
